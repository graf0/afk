# Przepływ Factory i Chat

Factory wzorowana na `ralph.sh` z dfmx; bez TUI ma go zastąpić już w pierwszym kamieniu milowym. `afk` pracuje na Project z bieżącego katalogu — bez `.afk.toml` odmawia.

## Factory

`afk factory [selektor]` bierze tylko Ticket z labelem `[labels].ready_for_agent` — bez niego odmawia, bez flagi obejścia. Selektor: `*` (domyślny — kolejne gotowe Tickety, jak `pick()` w ralph.sh, do wyczerpania kolejki) albo lista numerów `#12 #15` (w tej kolejności, potem koniec; zamknięty albo niegotowy ticket z listy to błąd, zablokowany jest pomijany z ostrzeżeniem). Bez limitu iteracji: `*` kończy się, gdy nie ma czego wziąć; Ctrl-C przerywa (VM bieżącego Run zostaje, jak po porażce).

1. `*` czyta z Forge listę otwartych issue z labelem `ready-for-agent` (rosnąco po numerze) i każdy kandydat sprawdza na świeżym odczycie — lista po labelu bywa nieaktualna. Pomija: ticket bez labela, dziecko Spec (robi je Spec), ticket z otwartym blokerem (patrz [Blokery](#blokery)), Spec z otwartym dzieckiem bez `ready-for-agent`, Spec bez dzieci i ticket z sub-issues bez labela `[labels].spec` (trzy ostatnie z ostrzeżeniem, raz), ticket zarezerwowany przez inną Factory oraz ticket już obsłużony w tym uruchomieniu. Z selektorem-listą ticket z sub-issues bez labela `[labels].spec` to błąd (Factory staje), pozostałe pominięcia są ostrzeżeniem.
2. Rezerwacja: `flock` na `~/.local/state/afk/claims/<project>/<n>`; spec rezerwuje też swoje otwarte dzieci. Po rezerwacji ticket jest czytany jeszcze raz (inna Factory mogła go skończyć w międzyczasie). Blokada znika ze śmiercią procesu. Jeden host — dwie maszyny z `afk` na tym samym repo są poza zakresem.
3. Preflight przed pierwszym Run (nie przy pustej kolejce): poświadczenia (Forge, Claude), istnienie wszystkich labeli z `[labels]` w repo (`afk` ich nie tworzy), Base image (patrz [Base image w Factory](#base-image-w-factory)) i klucz ssh, bramka `[gate].cmd` na czystym branchu bazowym w świeżej VM (niszczonej po teście). Gdy bramka pada, to nie wina Agenta: Factory kończy się błędem z ścieżką wyjścia bramki.
4. Spec (ticket z labelem `[labels].spec`) to ciąg Runów, jeden na każde dziecko w kolejności, na wspólnym branchu, zakończony review całości — patrz [Spec](#spec).
5. Każdy Run dostaje świeżą Sandbox VM (overlay na Base image). Po klonie, przed pierwszą sesją, `afk` uruchamia w `/work/repo` (klon) polecenia `setup` Tooli (alfabetycznie po nazwie, z `env` Tooli, sieć jak w Run); wyjście do `<log>-setup.txt`, porażka = porażka Run. Wznowienie w zostawionej VM pomija `setup`. `setup` i `env` dotyczą każdej świeżej VM, także preflightu i review Spec: bramka musi mieć to samo środowisko co Agent. Po sukcesie VM jest niszczona.
6. Runy jednej Factory idą po kolei. Równoległość = kilka Factory.
7. Porażka Run zatrzymuje Factory z kodem wyjścia ≠ 0; VM zostaje do inspekcji (`afk vm list`, `afk vm shell <vm>`; `afk vm kill <vm>` niszczy). `needs_info` Ticketu nie jest porażką — VM jest niszczona, Factory idzie dalej (także gdy `needs_info` zatrzymało Spec: pytania są na dziecku i na Spec). Nie ma TTL — nie wiadomo, ile co trwa.
8. Wznowienie: na starcie, przed kolejką, Factory szuka Runów tego Project zostawionych w VM (z metadanych domen libvirt; numer ticketu z id maszyny `<n>-<losowe>`). Przed ruszeniem czegokolwiek Factory bierze rezerwację ticketu leftovera (VM żywego Run innej Factory wygląda tak samo; zajęta → pomijana) i trzyma ją dla wznowionego Run; VM preflightu ma własną rezerwację `preflight-<vm>` na czas życia. Z selektorem-listą ruszane są tylko leftovery wymienionych ticketów i ich Specs. Ticket zamknięty → VM niszczona, w Quarantine repo znikają refy brancha, a branch `ticket-<n>` znika z remote tylko wtedy, gdy nie ma PR i nie ruszył się od odczytu (branch z PR nigdy); dla dziecka Spec ginie tylko VM — jego praca jest na branchu Spec. Wznowienie przepisuje `TICKET.md` (i `SPEC.md`) w VM ze świeżego odczytu. Ticket z `ready-for-agent` → Run kontynuowany w zostawionej VM, bez ponownego klonu, z notą „wznawiasz przerwaną pracę” w prompcie pierwszej sesji (jak `resume` w ralph.sh); VM dziecka Spec wznawia Spec, a VM review — review. Baza Run to ta z Quarantine repo (z początku przerwanego Run), nie dzisiejszy `origin/main`. Ticket bez labela → pominięty, VM zostaje (komunikat). VM po preflight zostawiona przez Ctrl-C jest niszczona. VM wyłączona (restart hosta) nie jest uruchamiana: wznowienie kończy się błędem ssh, `afk vm kill` i nowy Run.

Ścieżka logu Run jest wypisywana na starcie Run.

Forge: GitHub i Gitea przez REST (`net/http`), interfejs `Forge`. Token Gitei: `GITEA_TOKEN`, a bez niego `~/.local/state/afk/gitea-token` (`0600`). Słownik labeli konfigurowalny (`[labels]`), domyślnie z `docs/agents/triage-labels.md`.

#### Blokery

Bloker ticketu to każde issue z natywnej zależności Forge **lub** z linii `Blocked by: #a, #b` w treści (suma, nie pierwszeństwo — dopisanie zależności w UI nie unieważnia linii). Ticket jest odblokowany, gdy wszystkie blokery są zamknięte. Gitea z wyłączonymi zależnościami w repo: liczy się sama linia.

#### Base image w Factory

Przed każdym Run Factory sprawdza najnowszą wersję Base image każdej potrzebnej maszyny i buduje nową, gdy jej brak, minęło Expiry (`max_age`) albo hash konfiguracji obrazu różni się od bieżącego (starszych wersji z pasującym hashem nie szuka). Konfiguracja zawsze z gałęzi bazowej (ADR-0010). Wiek wersji wynika z jej nazwy (czas budowy); `max_age = "0"` wyłącza Expiry. Brak pliku `config-hash` w wersji = inny hash. Budowa pod `flock` per Project (`~/.local/state/afk/<project>/image.lock`); po zdobyciu blokady decyzja jest podejmowana jeszcze raz (inna Factory mogła właśnie zbudować), a druga Factory czeka na blokadę zamiast budować równolegle. Obraz jest zapewniany, gdy powstaje nowa VM z Base image: przed preflightem, przed każdym świeżym Run i przed każdą nową VM w Spec (dziecko, review), bo Spec trwa godzinami; wznowienie w zostawionej VM go nie wymaga (overlay ma własny backing file). Gałąź bazowa jest czytana raz na Run i ta sama konfiguracja idzie do obrazu, preflightu i Run. Log w `~/.local/state/afk/<project>/logs/image-<maszyna>-<wersja>.log`, na stdout jedna linia z powodem (`= image sandbox: building (no image | expired 170h0m0s > 168h0m0s | configuration changed), log: …`); porażka budowy kończy Factory. Po udanej budowie znikają wersje, które nie są najnowsze, nie są poprzednią najnowszą i nie są backing file żadnego overlayu w `runs/` ani `chats/` (szczegóły: [images.md](images.md)).

### Co dostaje agent

- Host zapisuje Ticket (treść, komentarze, spec, blokery) do pliku w VM, np. `/work/TICKET.md`.
- Prompt mówi: gdzie są dane, że tracker jest celowo niedostępny, że nie wolno zgadywać (ADR-0003).
- `CLAUDE_CODE_OAUTH_TOKEN` jako zmienna środowiskowa sesji ssh, nigdy na dysku obrazu.
- WebFetch/WebSearch wyłączone; sieć tylko przez Egress proxy z allowlistą. Odmowy proxy (host, port, powód) idą do `<log>-egress.txt`, na koniec Run jedna linia podsumowania.
- Toole: sekcja „Narzędzia” w prompcie każdej sesji (`prompt` każdego Toola i nazwy zmiennych z `env`); `env` Tooli ustawione w sesji Agenta i w bramce (ADR-0011).
- Skille z repo (`.claude/skills/`): w klonie. Pluginy: tylko te zadeklarowane w Project config, zainstalowane w Base image przy budowie — patrz [Pluginy](#pluginy). Nic z `~/.claude` hosta (ADR-0009).

### Raport agenta

Agent kończy sesję plikiem raportu:

- `status`: `done` | `needs_info`
- `summary`, `deviations` (odstępstwa od ticketu), `doubts` (wątpliwości dla reviewera)
- przy `needs_info`: lista pytań

`needs_info` → `afk` komentuje ticket pytaniami, ustawia `needs-info`, zdejmuje `ready-for-agent`; VM jest niszczona, wyniku się nie pobiera. Agent Factory nie rozmawia z człowiekiem (bez `ask_human`): część interaktywna dzieje się w Chat, przed Factory.

Strumień Agenta (stream-json) idzie do pliku logu w `~/.local/state/afk/<project>/logs/`, a na wyjście `afk` tekst Agenta i jednolinijkowe wywołania narzędzi, bez znaków sterujących i formatujących (gość jest niezaufany). Log jest rotowany: po 128 MiB przechodzi do `<log>.1` (poprzedni `.1` znika), więc na dysku najwyżej ok. 256 MiB, a Run nie jest przerywany z powodu rozmiaru; najstarsza część strumienia przepada.

### Po sesji

1. **Gate**: `[gate].cmd` z `.afk.toml` uruchamiany w VM po `done`. Porażka → sesja naprawcza Agenta z końcówką wyjścia bramki w prompcie (napraw minimalnie, nie zmieniaj zakresu), do `[gate].max_fixes` sesji (poprawki z review mają osobny budżet); wyczerpanie albo status inny niż `done` → porażka Run (VM zostaje). Wyjście każdej próby w pliku obok logu Run (`<log>-gate-N.txt`). Raport sesji naprawczej dopisuje się do raportu Run; sesja naprawcza → `ready-for-human`. Każda nowa porcja commitów z VM przechodzi tę samą walidację co pierwsza (przodek bazy, chronione ścieżki).
2. **Review** modelem `[agent].review_model`: sesja na całym branchu względem bazy, poprawia znaleziska i commituje. Poprawki → osobny commit `code review: <tytuł>` (też przez bramkę, z własnymi sesjami naprawczymi). Raport review (`findings_fixed`, `findings_skipped`) to drugi komentarz na PR; niepuste `findings_skipped` → `ready-for-human`.
3. **Git** (ADR-0002): host robi tylko `git fetch` / import `git bundle` z VM do Quarantine repo; nigdy nie uruchamia niczego w klonie agenta. Walidacja: zmiany w chronionych ścieżkach (`[protect]`, zawsze `.afk.toml`, `.github/`, `.gitea/` oraz na dowolnej głębokości `**/.claude/` i `**/.mcp.json` — hooki, pluginy i serwery MCP Claude'a uruchamiają się potem na hoście człowieka, także z podkatalogów) → odrzucenie. Sprawdzany jest każdy commit, bez wykrywania rename, z pominięciem wielkości liter; zastąpienie katalogu nadrzędnego plikiem lub symlinkiem też się liczy. `CLAUDE.md`, `.gitattributes`, `.gitmodules` są dozwolone. `.afk.toml` czytany zawsze z gałęzi bazowej.
4. Push i PR wyłącznie przez `afk` z poświadczeniami hosta. Commity implementacji są squashowane w Quarantine repo do jednego commita na bazie (`<tytuł ticketu> (#N)`, treść: `summary`, autor: tożsamość gita użytkownika z jego repo), a poprawki review do drugiego, `code review: <tytuł>`, na wierzchu; oba walidowane ponownie. Push `ticket-N` z Quarantine repo idzie na `https://github.com/<repo>.git` (Gitea: `<forge.url>/<repo>.git`) tokenem Forge w nagłówku HTTP przekazanym gitowi przez zmienne `GIT_CONFIG_*` (nie na argv, nie na dysku, tylko do tego procesu gita), bez globalnego i systemowego configu gita użytkownika (żadne `insteadOf` nie przekieruje go na ssh ani inny host), bez przekierowań HTTP i bez credential helperów; tylko tworzy branch, nigdy go nie nadpisuje. Branch `ticket-N` na remote → odmowa przed startem VM. Potem PR (draft; na Gitei draft = prefiks tytułu `WIP:`, zdjęty przy przejściu do gotowego — nie zdejmuj go ręcznie z PR Specu w trakcie, bo Factory nie wznowi Specu, którego PR nie jest draftem) z `Closes #N`, komentarz z raportem, `ready-for-human` na PR przy odstępstwach lub wątpliwościach, zdjęcie `ready-for-agent`. Tekst Agenta na GitHubie i w commicie: bez @-wzmianek i bez słów zamykających issue (`Fixes #12` itp.) — oba łamane zero-width space — bez komentarzy HTML (`<!--` → `&lt;!--`), najwyżej 60000 bajtów; własne `Closes #N` `afk` dopisuje po tym. Porażka kroku w Forge podaje, co zrobiono, i po linii na każdy krok do zrobienia ręcznie.

### Spec

`afk factory '#N'`, gdy N ma label `[labels].spec` (zachowanie jak `do_spec` w `ralph.sh`): ciąg Runów na branchu `ticket-<spec>`, zakończony review całego brancha.

- **Dzieci**: na GitHubie sub-issues, na Gitei (bez sub-issues) referencje `#M` z listy zadań `- [ ] #M` w treści Spec — stan z odczytu issue, checkboxy ignorowane; referencja do PR albo innego repo to błąd. Otwarte dzieci rosnąco po numerze; za każdym razem pierwsze bez otwartego blokera ([Blokery](#blokery)). Otwarte dzieci wszystkie zablokowane → porażka. Każde otwarte dziecko musi mieć `ready-for-agent` (jak `pick()` w `ralph.sh`), inaczej odmowa przed pierwszą sesją: gotowość nadaje człowiek (ADR-0003). Dzieci ze swoimi dziećmi nie są obsługiwane. Ticket bez labela Spec z listą zadań na Gitei to zwykły ticket — lista to checklista.
- **Run dziecka**: świeża VM; klon startuje z końca brancha `ticket-<spec>` (pierwsze dziecko: z bazy), `origin/<baza>` w klonie zostaje bazą. Prompt dostaje dziecko (`/work/TICKET.md`) i Spec jako kontekst (`/work/SPEC.md`: „kontekst, nie zakres”). Bramka przechodzi dla każdego dziecka; implementacja dziecka jest squashowana do jednego commita `<tytuł dziecka> (#M)` na końcu brancha. Walidacja: wynik sesji musi zawierać koniec brancha i nie dotykać chronionych ścieżek, a po squashu cała gałąź — bazę i te same chronione ścieżki. Review dziecka nie ma; jest jedno, na końcu.
- **Po dziecku**: push brancha; po pierwszym dziecku draft PR (tytuł Spec) z `Closes #<spec>` i `Closes` dla wszystkich dzieci; komentarz z raportem dziecka na PR; `ready-for-human` na PR, gdy dziecko miało odstępstwa, wątpliwości albo sesję naprawczą bramki (od razu, bo Run może być wznowiony w innym procesie); komentarz na dziecku z odnośnikiem do PR, zamknięcie dziecka, zdjęcie z niego `ready-for-agent`.
- **`needs_info` na dziecku**: komentarz z pytaniami i `needs-info` na dziecku oraz komentarz i `needs-info` na Spec, zdjęcie `ready-for-agent` z obu, porażka Spec (Factory idzie dalej). Zrobione dzieci zostają na branchu i na PR (draft). Aby Spec ruszył ponownie, człowiek przywraca `ready-for-agent` na dziecku i na Spec.
- **Review całości**: po ostatnim dziecku jedna sesja review (jak w Run) w świeżej VM na końcu brancha, względem bazy; poprawki to osobny commit `code review: <tytuł Spec>`, przez bramkę i walidację. Potem: push, komentarz z raportem review, nowy opis PR (`Closes` i lista commitów brancha), `ready-for-human` przy poprawkach bramki albo pominiętych znaleziskach, PR gotowy do review (GraphQL `markPullRequestReadyForReview`: REST tego nie umie), zdjęcie `ready-for-agent` ze Spec.
- **Wznowienie**: branch `ticket-<spec>` na remote z draft PR (albo bez PR) → kontynuacja od następnego otwartego dziecka, a gdy żadne nie zostało — od review. Czubek brancha z remote wchodzi do Quarantine repo i przechodzi tę samą walidację, a baza to merge-base z bieżącą bazą (branch bazowy mógł pójść naprzód). PR niebędący draftem albo zamknięty → błąd z instrukcją (zakończ lub zamknij PR, usuń branch `git push origin --delete ticket-<spec>`, uruchom ponownie); wynik z poprzedniego procesu zostawiony w Quarantine repo (porażka kroku w Forge) trzeba usunąć ręcznie, jak przy Run.
- **Push na istniejący branch** jest bezpieczny: `--force-with-lease=<ref>:<sha>`, gdzie sha to ostatni commit, który `afk` wypchnął albo odczytał; nowy commit zawsze leży na starym, więc to tylko fast-forward, a cudzy push pomiędzy kończy się odmową. Pierwszy push tworzy branch (lease z pustym sha). Nigdy blind force.

## Chat

`afk chat new <nazwa> [--model …] [--effort …]`, `attach <nazwa>`, `export <nazwa>`, `shell <nazwa>` (bash w VM z tym samym Egress proxy, bez `afk-forge`, bez blokady Chat), `rm [--force] <nazwa>`, `list`. Nazwa wymagana: `[a-z0-9-]{1,32}`, nie zaczyna się od `-`, unikalna w Project; Chat o tej nazwie albo branch `chat-<nazwa>` na remote → odmowa przy tworzeniu.

- `afk chat <nazwa> --expose` publikuje porty z `[expose]` (`.afk.toml` z gałęzi bazowej) w Stacku Chatu; bez flagi nie jest publikowany żaden port, a Run (Factory) nigdy ich nie publikuje (porty z `compose.yml` też są zawsze usuwane). Bez adresu bind na `127.0.0.1`, `0.0.0.0` daje ostrzeżenie na terminalu. Port hosta jest unikalny w `[expose]` (blokada jest per numer portu, niezależnie od adresu); adres tylko IPv4. Przed `Up` (po `Down` poprzedniego Stacku) proces bierze `flock` na `~/.local/state/afk/expose-locks/port-<port_hosta>.lock` (`<project>/<chat>` w treści) i próbuje `net.Listen` na `adres:port`: port trzymany przez inny Chat → błąd z nazwą Chatu, zajęty przez coś innego → błąd z portem; blokada trwa do `Down` Stacku Chatu (albo śmierci procesu). Serwis z `[expose]` nieobecny w Stacku → błąd przy starcie; `--expose` bez `[expose]` → błąd.
- Własna, długo żyjąca Sandbox VM; kod to snapshot gałęzi bazowej z chwili utworzenia, bez synchronizacji (świeży stan = nowy Chat). `setup` i `env` Tooli jak w Run (log `<log>-setup.txt`).
- Claude Code interaktywnie na pty po ssh, `--dangerously-skip-permissions`; model z `[agent]` (do nadpisania `--model`), effort tylko flagą `--effort` (`claude --effort`); oba w metadanych VM. Brak Base image albo nieaktualny → budowany jak w Factory. Porażka przed startem `claude` usuwa VM, stan i refy Chat (zostają logi); po starcie Chat zostaje zawsze.
- Cały internet przez Egress proxy (bez adresów prywatnych i hosta), odmowy do `chat-<nazwa>-<czas>-egress.txt` (logi per proces, jak w Run: także `-setup.txt`). Token i kod uznajemy za możliwe do wyniesienia (ADR-0003).
- `--append-system-prompt` od `afk`: izolowana VM, brak `gh` i Forge, tickety przez `afk-forge`, kod to snapshot, eksport tylko przez `afk`, pełny internet.
- Proces `attach` trzyma ssh, Egress proxy, kanał `afk-forge` i pty; `flock` na `~/.local/state/afk/<project>/chats/<nazwa>/lock` — drugi `attach` dostaje odmowę z PID właściciela. Koniec `claude` (`/exit`, crash) kończy proces, VM zostaje; kolejny `attach` uruchamia `claude --continue` (bez flagi, gdy w gościu nie ma jeszcze rozmowy), z modelem i effortem z metadanych VM oraz `env` Tooli i gałęzią bazową z chwili utworzenia Chat (`snapshot.json` w stanie Chat), nie z dzisiejszej bazy. Wyłączona VM (restart hosta) jest startowana przy `attach`, `export` i `rm`; bez autostartu przy boocie.
- Shell w VM Chat (`M-s`): to samo Egress proxy, bez kanału `afk-forge`.
- Pluginy i skille: to samo co w Factory, czyli co jest w obrazie i w repo; nic z `~/.claude` hosta (ADR-0009).

### `afk-forge`

ADR-0012. Binarka `afk` kopiowana przy `attach` do `/usr/local/bin/afk-forge`; woła `afk` przez odwrotny unix socket na ssh (HTTP+JSON), istniejący tylko przy `attach`. `afk` wykonuje operacje swoim tokenem, tylko dla Forge tego Project:

- `issue view <n>` — format `TICKET.md` (ta sama sanitizacja); `issue list [--label …] [--state open|closed|all]` — `#N  [labele]  tytuł`.
- `issue create`, `issue comment` — treść ze stopką `— z Chat <nazwa>`. Komentarz na dowolnym issue, także `ready-for-agent`: trafia do `TICKET.md` Run, ale w Chat jest człowiek in-the-loop, więc to świadomy kompromis, nie dziura. Label Spec dozwolony — Chat tworzy Specy.
- `issue edit` — labele dowolnego issue; treść i tytuł tylko issue utworzonych przez ten Chat (lista numerów w `~/.local/state/afk/<project>/chats/<nazwa>/issues`) i tylko dopóki nie mają `ready-for-agent`: człowiek zatwierdził tę treść, więc jej zmiana omijałaby review (liczy się label sprzed zapisu, także gdy to samo wywołanie go zdejmuje). Label Spec na cudzym tickecie zmienia tryb Factory (ticket staje się Specem; jego dzieci i tak potrzebują `ready-for-agent`) — świadomie dozwolone.
- `issue comment` na pull requeście jest odrzucany jak `issue edit`; nieznane trasy kanału też trafiają do logu.
- `ready-for-agent` z Chat jest zamieniany na `needs-triage` — gotowość dla Factory nadaje człowiek. Bez zamykania issue.
- `pr create --title … [--body … | --body-file -]` (ADR-0014): commity klonu Sandboxa (`git bundle` przez `Exec`) idą do Quarantine repo, z walidacją jak wynik Run (przodek bazy, chronione ścieżki z `[protect]` i Dockerfile'e Stacku); naruszenie → odmowa z listą commitów i ścieżek, nic nie trafia do Forge. Bez commitów względem bazy → błąd; niezacommitowane zmiany nie wchodzą (ostrzeżenie). Push `chat-<nazwa>` z `--force-with-lease` na koniec, który `afk` zostawił (pierwszy: brak brancha) — cudzy push → odmowa. Potem PR gotowy do review (nie draft) z treścią ze stopką Chat; gdy PR z tego brancha jest otwarty, tylko push i URL (tytuł i opis bez zmian).
- `stack logs <serwis> [--tail <n>]` — ogon logu serwisu Stacku Chatu (domyślnie 100 linii, max 1000; poza zakresem → błąd; wynik sanityzowany i obcięty do 256 KiB). `stack restart <serwis>` — dowolny serwis poza `afk` (Sandbox Agenta) i jednorazowym `afk-setup` (→ `stack reseed`). `stack reseed` — ponowne `afk-setup` (Stack bez tego serwisu → błąd); czyści tyle, ile czyści skrypt Projectu, volume'y zostają. Wyjście restartu i reseedu wraca do Agenta (sanityzowane, ten sam limit), nigdy na terminal, na którym działa claude. Nazwa serwisu musi być na liście `docker-compose config` (nieznana → 400 z listą); polecenia idą jako argv do `docker-compose`, nigdy przez powłokę. Restart i reseed jeden naraz.
- `vm …` — VM testowe z `[[vm]]` (istniejące domeny libvirt, sterowane przez `virsh` jako argv, nigdy przez powłokę): `list` (stan, os, user, właściciel, adres), `start`, `shutdown` (ACPI), `screenshot <vm> [--file]` (PNG zapisany w Sandboxie), `key <vm> ctrl+alt+delete` (max 6 klawiszy z listy dozwolonych), `type <vm> <tekst>` (US ASCII, max 500 znaków), `click`/`move <vm> [--button] <x> <y>` (piksele ostatniego screenshotu, skalowane na osie abs QMP 0..32767; bez screenshotu → 400), `snapshot`/`revert <vm> <nazwa>` (`[A-Za-z0-9][A-Za-z0-9_.-]{0,63}`), `release`. Tylko VM z `[[vm]]` (inna → 400). Lock: pierwsza zmieniająca operacja (nie `list`, nie `screenshot`) zajmuje VM dla Chatu — `flock` na pliku `~/.local/state/afk/vm-locks/vm-<domena>.lock` (`<project>/<chat>` w treści, tylko do wyświetlenia; o zajętości decyduje wyłącznie `flock`), widoczny dla wszystkich procesów `afk chat` na hoście, zdejmowany przez `release`, koniec procesu albo jego śmierć; inny Chat dostaje 409. Klucz ssh (ed25519, `ssh-keygen`) jest jeden per Project w `~/.local/state/afk/<project>/vm-ssh/`, generowany raz (przez `afk config` albo pierwszy Chat) i montowany tylko do Sandboxa Chatu razem z konfiguracją ssh (`~/.ssh/config`, alias per VM z `user`); `afk config` wypisuje część publiczną. Run (Factory) nie ma klucza ani tras VM. Klawisze i mysz idą przez `virsh qemu-monitor-command` (QMP `input-send-event`), co libvirt odnotowuje jako taint domeny (`custom-monitor`); mysz wymaga absolutnego urządzenia wskazującego w VM (np. `usb-tablet`).
- Każde wywołanie (operacja, numer, wynik) do `~/.local/state/afk/<project>/logs/chat-<nazwa>-<czas>-forge.txt`.

### Eksport

Na żądanie człowieka, wielokrotnie, bez `attach` (własne ssh; wyłączona VM jest startowana). Wszystkie commity od snapshotu bazy (`HEAD` z chwili wywołania) idą `git bundle` do Quarantine repo, bez squasha, z tą samą walidacją co wynik Run (przodek bazy, chronione ścieżki). Chronione ścieżki są z `.afk.toml` z chwili utworzenia Chat (snapshot). Naruszenie → odrzucony cały eksport; komunikat wymienia każdy naruszający commit (krótki sha i temat) z jego chronionymi ścieżkami, a człowiek każe Agentowi poprawić historię w Chat. Niezacommitowane zmiany w VM nie blokują eksportu: commity idą, a `afk` ostrzega, że zmian nie wyeksportowano. Bez nowych commitów (`HEAD` równy ostatnio wyeksportowanemu, a bez eksportu bazie) komunikat i brak pushu. Push `chat-<nazwa>` z `--force-with-lease=<ostatnio wypchnięty sha>` (pierwszy: pusty sha) — przepisana historia przechodzi, cudzy push na branch kończy się odmową. Ostatnio wypchnięty sha zapisuje `afk` w stanie Chat (`snapshot.json`, zapis atomowy) dopiero po udanym pushu; branch na remote już na `HEAD` (push bez zapisu po crashu) jest tylko zapisywany, a branch usunięty na remote przez człowieka — tworzony od nowa. `HEAD` cofnięty do bazy po eksporcie: komunikat, branch na remote zostaje. Bez PR.

### Zamknięcie

`afk chat rm [--force] <nazwa>` niszczy VM (domena, sieć, filtr, overlay), refy Quarantine `chat-<nazwa>` i stan Chat (`snapshot.json`, blokada). Logi i branch `chat-<nazwa>` na remote zostają. Bierze blokadę Chat: trzymana przez `attach` → odmowa z PID właściciela, także z `--force`.  Odmowy, które `--force` znosi, kończą się kodem wyjścia 3 (TUI pyta wtedy o `--force`).

Bez `--force` odmawia, gdy w VM są niezacommitowane zmiany (także pliki nieśledzone) albo `HEAD` ma commity nieosiągalne z ostatniego eksportu (`snapshot.json`), a bez eksportu z bazy snapshotu (ref bazy w Quarantine repo); komunikat podaje liczbę ścieżek z niezacommitowanymi zmianami i liczbę oraz krótkie sha (do 5) takich commitów. `HEAD` poza historią eksportu (przepisana historia) też jest odmową; `HEAD` cofnięty za eksport nie (wszystko w nim wyeksportowano). Pliki ignorowane przez git i historia rozmowy `claude` w VM giną bez ostrzeżenia. Wyłączona VM jest startowana do sprawdzenia (ssh jak w `export`, bez Egress proxy) i po odmowie zostaje uruchomiona. `--force` nie sprawdza niczego i nie startuje VM.

Kolejność: VM, refy Quarantine, na końcu katalog stanu — przerwane `rm` zostawia Chat, który `rm` nadal usunie. Resztki: katalog stanu bez VM (nic do utracenia) jest usuwany razem z refami bez `--force`; VM bez katalogu stanu (nie wiadomo, co wyeksportowano) wymaga `--force` (usuwa VM i refy); nieznana nazwa → błąd. Katalog stanu bez czytelnego `snapshot.json` albo bez refu bazy, przy istniejącej VM, też wymaga `--force`. TUI przy `M-x` pyta: eksportuj / usuń / anuluj.

### Pamięć

Przed utworzeniem każdej VM (Chat, Run, preflight, dziecko i review Spec) `afk` sprawdza `MemAvailable` hosta: mniej niż `memory` maszyny + 2 GiB → odmowa z czytelnym błędem; Factory kończy się wtedy jak przy porażce preflightu (bez VM do inspekcji). Bez balloona i kolejkowania: to odczyt w chwili startu, więc dwie VM tworzone naraz mogą przejść oba. Budowa Base image (Packer, poza libvirt) nie jest sprawdzana.

## Pluginy

Agent dostaje wyłącznie pluginy wymienione wprost (ADR-0009): `[agent].plugins` (`<nazwa>@<marketplace>`) i `[agent].marketplaces` (`owner/repo` albo URL gita) z `.afk.toml` oraz `enabledPlugins` (włączone) i `extraKnownMarketplaces` (źródło `github` lub `git`) z `.claude/settings.json` Project. `afk image build` dodaje marketplace'y (`claude plugin marketplace add`, zawsze też `anthropics/claude-plugins-official`, gdy jest jakikolwiek plugin) i instaluje pluginy (`claude plugin install --scope user`); `github.com` jest dozwolony przez Egress proxy budowy. `afk` sprawdza tylko format id i że źródło nie zaczyna się od `-`, resztę (brak pluginu, marketplace'u) zgłasza `claude` przy budowie. Zmiana listy wymaga przebudowy obrazu; ustawienia i `.afk.toml` są czytane z gałęzi bazowej (`origin/HEAD`) i przy budowie, i przez Run (brak pliku = brak pluginów). Pluginy LSP potrzebują binarki w obrazie (np. `gopls` w `[machine.sandbox].build`).

Gdy efektywna lista zawiera `mattpocock-skills`, prompt Run zaczyna się od `/mattpocock-skills:implement`, a prompt review od `/mattpocock-skills:code-review <baza>` (jak w `ralph.sh`); bez niego zostają zwykłe prompty.

Z `~/.claude` nigdy nie trafia do VM: `.credentials*`, `settings.json` (hooki, uprawnienia), `projects/` (pamięć i transkrypty innych projektów), `history.jsonl`, `session-env/`, `plans/`, `file-history/`, `skills/synced/` (skille konta claude.ai, zakładają connectory).

## TUI

ADR-0008. `afk tui`: osobny serwer `tmux -L afk` z konfiguracją wbudowaną w `afk` (bez `~/.tmux.conf`), tmux ≥ 3.3 sprawdzany przy starcie (reszta `afk` działa bez tmux). Lewy panel: `afk sidebar` (bubbletea), pogrupowany po Project: Chaty i porzucone Runy (VM po porażce) wszystkich Project z metadanych domen libvirt, Factory z opcji okien tmux (`@afk-kind`, `@afk-project`, `@afk-repo`, ustawiane przez TUI przy tworzeniu okna) — Factory uruchomiona poza TUI widać tylko przez VM jej Run. Każdy Chat i Factory to okno tmux z procesem `afk`; zamknięcie terminala ich nie przerywa (`detach`/`attach`). Metadane domeny i okna zawierają ścieżkę repo Project: `M-n` i `M-F` działają dla Project zaznaczonego wpisu, potem bieżącego katalogu, inaczej odmowa.

Skróty bez prefiksu, reszta klawiszy idzie do Agenta. Zajęte przez Claude Code i do omijania: `M-f`, `M-b`, `M-d`, `M-y`, `M-p`, `M-t`, `M-o`, `M-v`, `M-m`, `M-Enter`; `M-↑/↓` przewija w Claude Code listę plików diff (jest też Ctrl+↑/↓).

| Klawisz | Akcja |
|---|---|
| `M-↑` / `M-↓` | poprzedni / następny wpis |
| `M-n` | nowy Chat (pyta o nazwę) |
| `M-F` | nowa Factory (pyta o selektor, domyślnie `*`) |
| `M-x` | zamknij Chat (eksport / usuń / anuluj) / Factory: działającą przerywa jak Ctrl-C po potwierdzeniu, zakończoną zamyka (okno) / zniszcz VM porzuconego Run |
| `M-e` | eksport Chat |
| `M-s` | shell w VM (Chat, porzucony Run; przy Factory tylko komunikat) |

Widok Factory: okno z `afk factory` — strumień bieżącego Run tylko do odczytu (tekst Agenta, jednolinijkowe wywołania narzędzi, zdarzenia `afk`: bramka, review, push). Nagłówek: `afk factory` na TTY co ok. 10 s ustawia tytuł sekwencją OSC 2 (numer i tytuł ticketu, wiek Run, czas od ostatniego zdarzenia), tmux pokazuje go przez `pane-border-status`. Okno ma `remain-on-exit`: po końcu Factory zostaje z wyjściem i kodem wyjścia do `M-x`.

## Stan
