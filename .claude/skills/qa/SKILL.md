# QA

Given a PR number (open or merged), produce **one** GitHub issue holding a checklist a human walks through by hand. The checklist holds **only what automated tests do not cover and what can be done through the UI or from an agent** (sftp/ssh clients count as user surface). Database, foreign keys, migrations and internal functions are the tests' job, never a QA task.

You never perform the tasks yourself and you never click through the UI. You read, run the test suite, and write the list.

The issue tracker, labels and domain docs are described in `docs/agents/`. Read `GLOSSARY.md` and any ADR touching the area first.

## Process

### 1. Gather

- `gh pr view <n> --json title,body,state,files` and `gh pr diff <n>`.
- Every issue the PR closes (`Closes #N`): read the body, especially acceptance criteria.
- All PR comments, reviews and inline comments. Agents list what they did not verify under headings like "Wątpliwości do sprawdzenia" or "Pominięte w review", and in phrases like "nie sprawdzałem w przeglądarce". These are the best bug leads.

### 2. Establish facts

- Run `go test ./...` and read the tests for the touched behaviour (names and bodies, don't guess). Use them to **drop** candidate tasks: a test that checks the same behaviour on the same surface means no task. A lower-layer test does not cancel a UI task. If tests fail, that goes first in the ticket.
- Take run commands from `Taskfile.yml` and `README.md`, not from memory. Note prerequisites the repo can't provide (a Windows machine, wine, a second host).

### 3. Draft tasks

One task per **behaviour a human can observe**, not per file. Sources:

1. Acceptance criteria of each closed issue.
2. The diff, for changes no issue mentions (migrations, new endpoints, sftp/ssh/agent changes).
3. Agent comments from step 1.

**Scope.** A task must be doable through the UI, from an agent, or with an sftp/ssh client. The test: _does the application let a user do this?_ If the only way is poking the database or calling internals, it is not a task. Prefer scenarios that cross layers (create a config in the UI, then try to delete its recipe over sftp) over single-screen checks, but only when no test covers them. Format and example: [TASK-FORMAT.md](TASK-FORMAT.md).

**No filler.** The ticket lists only things to do. No lines about what did not change ("brak nowych zależności", "platformy nieistotne", "pominięto jako pokryte"). Omit empty sections.

**Platforms.** Ask of every change: _could this behave differently on another OS, architecture or client?_ Signals: agent or transport code, file paths, permissions, line endings, encoding, sftp/ssh as seen from a real client, anything browser-dependent. If so, write separate checkboxes per platform (Linux and Windows, Chrome and Firefox, ...). If no signal is present, add nothing.

### 4. Show the draft, then publish

Print the draft in the terminal and wait for the user's go-ahead. Only then create the issue. If no task survives, say so in the terminal and create no issue.

- Title: `QA: PR #<n> <PR title>`.
- Label: `ready-for-human` only (no category label).
- Body in Polish, starting with `> *This was generated by AI.*`, then `Part of #<n>`.
- Sections, in order: **Przygotowanie** → **Podejrzane miejsca** → one section per closed issue → **Regresja** (sections without tasks are omitted).
- One issue, no sub-issues. The human decides what to do with failures; do not file bugs for them.
